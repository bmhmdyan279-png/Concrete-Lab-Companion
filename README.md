**نسخه ۴.۱.۰ – موتور محاسباتی جدا از نمایش، با ورودی دادهٔ واقعی کاربر**

نسخه ۴ محصول را از «اسکریپت تولید اکسل» به یک **سیستم محاسباتی/QA مدل‌محور** ارتقا داد:
علم آزمایش‌ها در پایتون محاسبه و با موارد طلایی راستی‌آزمایی می‌شود؛ اکسل فقط **نمایش**
نتایج است — بدون حتی یک فرمول محاسباتی در فایل.

نسخه ۴.۱ دو کار انجام می‌دهد: **مسیر ورودی دادهٔ کاربر** را اضافه می‌کند (تا محصول
فقط گزارش نمونه نباشد) و یک **لایهٔ تستِ سازگاری** می‌سازد تا هیچ ادعایی در
`config.yaml`، `README`، صفحهٔ فرود یا `CITATION.cff` نتواند دوباره از کد عقب بماند.

---

## ⚠️ پیش از دانلود: این فایل چه هست و چه نیست

فایل `.xlsx` منتشرشده یک **گزارش رندرشدّه** است، نه ماشین‌حساب. چون هیچ فرمولی در آن
نیست (و این با تست ساختاری در هر ساخت اثبات می‌شود)، تایپ کردن در سلول‌ها نتیجه‌ای را
تغییر نمی‌دهد. برای محاسبهٔ داده‌های آزمایشگاه خودتان از مسیر ورودی استفاده کنید:

```bash
python build.py --input examples/sample_input.json --output output
```

خودِ workbook هم این موضوع را پنهان نمی‌کند: شیت `00_راهنما` با یک بنر صریح اعلام
می‌کند که داده‌ها نمونه‌اند یا از فایل کاربر آمده‌اند، و `manifest` هر ساخت
`data_source` را ثبت می‌کند.

## 🏛 معماری

```text
standards DB (rulesets) → domain engine → validation/QA → Excel renderer (display-only)
```

| لایه          | مسیر                             | مسئولیت                                                                            |
| ------------- | -------------------------------- | ---------------------------------------------------------------------------------- |
| دامنه         | `src/concrete_lab/domain/`       | اشیای مقدار (`Quantity`, `ValidationStatus`) و موتور محاسبه                        |
| استانداردها   | `src/concrete_lab/standards/`    | رولسیت‌های تایپ‌شده: `C39-26`, `C805-25`, `ISIRI 302 (1394)` + رجیستری حسابرسی‌شده |
| مشخصات آزمایش | `src/concrete_lab/specs/`        | کاتالوگ داده‌محور ۲۰ آزمایش (ثبت غیرمتمرکز، فصل‌به‌فصل)                            |
| ورودی کاربر   | `src/concrete_lab/cases.py`      | خواندن و اعتبارسنجی فایل JSON اندازه‌گیری‌ها پیش از رسیدن به موتور                 |
| QA            | `src/concrete_lab/qa/`           | اجرای واقعی pytest، سوئیت طلایی درون‌فرآیندی، بررسی ساختاری محصول                  |
| نمایش         | `src/concrete_lab/render/excel/` | رندر فقط‌نمایشی: مدل داده → شیت (بدون منطق)                                        |
| گزارش         | `src/concrete_lab/report/`       | Manifest با ردیابی کامل (نسخه‌ها، قوانین، QA، منبع داده، SHA-256)                  |
| ارکستراتور    | `build.py`                       | فایل کوچک ورودی؛ فقط راه‌اندازی و واگذاری به CLI                                   |

### مرز استاندارد و تخمین

- **ASTM C39/C39M-26**: فقط استوانه؛ هندسه مکعب با خطای صریح «خارج از دامنه» رد می‌شود
  (هرگز ضریب تجربی خودکار). اصلاح L/D با جدول منتشرشده و **درون‌یابی خطی**.
- **ASTM C805/C805M-25**: `scope=ESTIMATION` با بج «ESTIMATED — NOT FOR ACCEPTANCE» و سلب
  مسئولیت قوی دوزبانه؛ هیچ فرمول جهانی عدد بازگشت→مقاومت وجود ندارد و تخمین فقط با
  همبستگی اختصاصی پروژه ممکن است.
- **ISIRI 302 (ویرایش سوم، ۱۳۹۴)**: رولسیت کامل (پاکت دانه‌بندی + باند هشدار نزدیک مرز +
  قوانین فیزیکی منحنی). دو کمیت مشتق هم در همین لایه‌اند، نه در اکسل: تبدیل
  **جرم مانده روی الک** به منحنی درصد عبوری (با کنترل توازن جرم ASTM C136) و
  **مدولوس نرمی** (`fineness_modulus`) بر اساس سری الک‌های C136.

## 🚀 نصب و استفاده

```bash
pip install -r requirements-dev.txt     # زمان اجرا + ابزار تست
# یا بستهٔ نصب‌پذیر:
pip install -e ".[dev]"
```

```bash
# ساخت از دادهٔ نمونهٔ داخلی
python build.py --output output --no-protect

# ساخت از اندازه‌گیری‌های خودتان
python build.py --input examples/sample_input.json --output output

# اجرای واقعی QA (سوئیت طلایی + pytest) — خروجی غیرصفر در صورت شکست
python build.py --validate

# محدودکردن اعتبارسنجی به بخشی از تست‌ها
python build.py --validate tests/test_domain.py

# ممیزی محصول ساخته‌شده در برابر قرارداد نسخهٔ ۴
python scripts/audit_excel.py --output output
```

### فایل ورودی کاربر

یک JSON ساده؛ نمونهٔ کامل در `examples/sample_input.json`:

```json
{
  "project": { "name": "پل سرخه‌رود" },
  "cases": [
    { "test_id": "4-1", "inputs": { "geometry": "cylinder", "diameter_mm": 150, "length_mm": 300, "load_kn": 682.4 } },
    {
      "test_id": "1-1",
      "inputs": {
        "total_mass_g": 1000,
        "pan_g": 15,
        "retained": {
          "9.5": 30,
          "4.75": 80,
          "2.36": 170,
          "1.18": 210,
          "0.6": 180,
          "0.3": 140,
          "0.15": 135,
          "0.075": 40
        }
      }
    }
  ]
}
```

قواعد اعتبارسنجی (همه پیش از هر محاسبه، و همه با پیام قابل‌فهم):

- هر `test_id` باید توسط موتور پیاده‌سازی شده باشد؛ در غیر این صورت فهرست
  آزمایش‌های **موجود** در پیام خطا می‌آید.
- هر `test_id` فقط یک بار؛ هر آزمایش یک شیت مستقل دارد.
- همهٔ ایرادهای فایل **یک‌جا** گزارش می‌شوند، نه یکی‌یکی در هر اجرا.
- اگر حتی یک مورد رد شود، **هیچ فایلی ساخته نمی‌شود** (خروجی غیرصفر).

### سه سطح QA در هر ساخت

| سطح          | شرح                                                | کجا گزارش می‌شود            |
| ------------ | -------------------------------------------------- | --------------------------- |
| golden-suite | اجرای موارد طلایی مقابل موتور (درون‌فرآیندی)       | شیت `24_QA_Test` + manifest |
| structural   | تمامیت فایل، SHA-256، manifest، تضمین «بدون فرمول» | manifest                    |
| pytest-suite | کل سوئیت تست (با `--validate`)                     | خروجی خط فرمان              |

هشدارهای سوئیت طلایی **بی‌نام نیستند**: هر هشدار می‌گوید کدام فایل و چرا اجرا نشده
(معمولاً «این آزمایش هنوز در موتور پیاده‌سازی نشده»)، و همان فهرست در شیت
`24_QA_Test` چاپ می‌شود.

### حفاظت شیت‌ها

رمز از متغیر محیطی `WORKBOOK_PASSWORD` (یا `--password-env`) خوانده می‌شود و در نبود آن
از `config.yaml`؛ وضعیت `Protection: ENABLED/DISABLED` صریح لاگ و در manifest ثبت
می‌شود. ریلیزهای CI با `--no-protect` ساخته می‌شوند، یعنی **فایل منتشرشده محافظت‌شده
نیست**.

> حفاظت شیت فقط جلوی ویرایش تصادفی را می‌گیرد؛ **یک مرز امنیتی نیست.**

### پیکربندی

ترتیب یافتن فایل پیکربندی: `--config PATH` ← متغیر محیطی `CONCRETE_LAB_CONFIG` ←
جست‌وجوی `config.yaml` از مسیر بسته به بالا ← **مقادیر پیش‌فرض داخل کد**. به همین دلیل
بستهٔ نصب‌شده (`pip install`) بدون وجود `config.yaml` کنارش هم کار می‌کند.

### لایهٔ تستِ سازگاری

بیشترین ایراد این پروژه هرگز فرمول اشتباه نبود؛ **ادعایی بود که با کد نمی‌خواند**.
`tests/test_consistency.py` همان دسته را غیرممکن می‌کند:

- عدد `implemented`/`pending` در `config.yaml` باید با رجیستری زنده برابر باشد
  (پیش‌تر `20` نوشته بود در حالی که موتور ۷ آزمایش داشت).
- فهرست `key_sheets` باید **دقیقاً** همان شیت‌هایی باشد که رندر تولید می‌کند.
- `CALCULATORS` و specهای `implemented=True` باید یکی باشند.
- هر آزمایش پیاده‌سازی‌شده باید مورد طلایی **اجراشده** داشته باشد؛ در غیر این صورت
  شکست است، نه هشدار.
- نسخه باید در `__init__.py`، `pyproject.toml`، `config.yaml`، `CITATION.cff`،
  `landing/release.json` و `CHANGELOG.md` یکسان باشد.
- صفحهٔ فرود حق ندارد هش SHA-256 یا شمارهٔ نسخه را hard-code کند.
- هیچ وابستگی در `requirements.txt` اجازه ندارد استفاده‌نشده باشد.
- هیچ ماژولی در `src/` اجازه ندارد فرمول اکسل بنویسد و هیچ ماژول رندری اجازه ندارد
  رولسیت علمی وارد کند.

### اصول حاکم بر کد

- **منطق علمی فقط در پایتون** — رندر اکسل هیچ فرمولی نمی‌نویسد و تست ساختاری این
  قرارداد را در هر ساخت راستی‌آزمایی می‌کند (هم با پیشوند `=` و هم با
  `data_type == "f"` خود openpyxl).
- **وضعیت‌ها ساختاریافته‌اند** — `ValidationStatus` شش‌حالته؛ نمایش (✅/⚠️/❌) فقط در
  لایهٔ رندر.
- **ثابت‌های نام‌دار** به‌جای اعداد جادویی (`constants.py`)، با ذکر منبع استاندارد.
- **Docstring و type hints کامل** در همهٔ ماژول‌ها (با تست اجباری).
- **بدون کد مرده** — داربست‌های خالی حذف شده‌اند.
- **QA هرگز false-green نمی‌دهد** — اگر pytest پیش از اجرای تست‌ها متوقف شود، خروجی
  غیرصفر است؛ اگر یک مورد طلایی خراب باشد، شکست ثبت می‌شود نه کرش.
- **ردیابی**: هر نتیجه به نسخهٔ رولسیت خود (`C39-2026-v1`, …) ارجاع دارد و manifest
  هویت کامل ساخت را ثبت می‌کند — شامل `data_source` که می‌گوید داده نمونه بوده یا
  اندازه‌گیری کاربر.

### ساختار بسته

```text
src/concrete_lab/
```

## 🌐 صفحهٔ فرود و یکپارچگی فایل

هش SHA-256 روی صفحهٔ فرود **دستی وارد نمی‌شود**. `scripts/make_release_manifest.py`
آن را از manifest همان ساخت می‌خواند و در `landing/release.json` می‌نویسد؛ صفحه در
زمان بارگذاری همان فایل را می‌خواند. اگر خوانده نشود، به‌جای نمایش یک هش قدیمی،
صراحتاً «هش در دسترس نیست» می‌گوید.

CI در `build.yml` یک بار می‌سازد و **همان بایت‌ها** را هم به Release می‌فرستد و هم
هویتشان را به Pages می‌دهد؛ بنابراین هشِ روی سایت همیشه مربوط به فایلی است که
دانلود می‌کنید.

> فایل اکسل timestamp ساخت را در خود embed می‌کند، پس ساختِ دوبارهٔ آن توسط شما هش
> یکسانی تولید نمی‌کند. هش منتشرشده مربوط به **artifact همان ریلیز** است.
